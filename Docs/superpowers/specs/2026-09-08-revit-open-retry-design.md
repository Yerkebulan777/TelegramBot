# Одноразовый повтор открытия Revit-модели

## Цель

Автоматически повторять один раз задачу Revit, если AddIn записал валидный `ResultFile` со `status=failed`, а `errorDetails` подтверждает `Autodesk.Revit.Exceptions.InternalException` в `UIApplication.OpenAndActivateDocument`.

Это защищает очередь от разового сбоя Revit при загрузке модели. Механизм не пытается исправлять RVT, не перезапускает экспорт после его начала и не меняет жизненный цикл Revit: каждая попытка по-прежнему запускает отдельный процесс.

## Границы

- Меняется только `TelegramBot.Worker` и его документация.
- `RevitBIMFusion` продолжает записывать прежний `ResultFile`; XSD и XML-контракт не изменяются.
- Автоматический повтор не применяется к `cancelled`, отсутствующему или невалидному `ResultFile`, таймаутам, ошибкам запуска и обычным `status=failed`.
- Повтор не создаёт отдельную запись команды: используется существующая строка `Commands`, `RetryCount` и `ScheduleRetryAsync`.

## Классификация

`ResultAnalyzer` добавляет к `CommandResult` признак повторяемого сбоя открытия Revit. Он выставляется только когда одновременно выполнены условия:

1. команда является Revit-командой;
2. плагин вернул `status=failed`;
3. `errorDetails` содержит `Autodesk.Revit.Exceptions.InternalException`;
4. `errorDetails` содержит `UIApplication.OpenAndActivateDocument`.

Поиск выполняется без учёта регистра. Сопоставление по двум строкам намеренно узкое: общий `InternalException` может появиться после открытия или во время экспорта и не должен повторяться автоматически.

## Выполнение

`ProcessRunner` сохраняет общее правило: плагинный `failed` является постоянной ошибкой. Единственное исключение — отмеченный повторяемый сбой открытия Revit.

Для него Worker вызывает существующий `ScheduleRetryAsync`, если `RetryCount` исходной команды равен нулю. `NextRetryAt` задаётся на 10 секунд после обработки результата. Следующая попытка создаёт новый `TaskFile` и запускает новый `Revit.exe` через обычный pipeline.

Если повторная попытка снова получает этот же признак, Worker переводит команду в `Failed` без дополнительного retry. Финальное сообщение сохраняет исходную ошибку и добавляет ясное указание, что автоматический повтор открытия модели также завершился неудачей.

Другие retry-пути и их общий лимит `WorkerOptions.MaxRetries` остаются без изменений.

## Наблюдаемость

В лог Worker добавляются структурированные события:

- обнаружен повторяемый сбой открытия: command id, correlation id, команда, номер текущей попытки;
- запланирован целевой retry: command id, `RetryCount`, `NextRetryAt`;
- второй такой сбой переведён в финальный `Failed`.

`errorDetails` остаётся диагностическим полем и не отправляется пользователю целиком.

## Документация и проверка

`Docs/ExecutionAlgorithm.md` фиксирует исключение из правила «plugin `status=failed` без retry».

После реализации выполнить `dotnet build TelegramBot.slnx`. Отдельные тесты не добавляются по правилам репозитория; проверка сценария строится на небольших, явно переданных значениях `ResultFile` в существующих локальных границах классификации.
